# Эксплуатация, миграции и восстановление

## Production-конфигурация

Не переносить dev/test секреты. Заполнить `.env` вручную по env.example или сгенерировать
новые значения (32 случайных байта для SESSION_SECRET и паролей). Установить:
NODE_ENV=production, APP_ORIGIN=https://ваш-домен, COOKIE_SECURE=true, COOKIE_SAME_SITE=lax,
TRUST_PROXY=1 только при ровно одном доверенном Nginx. CORS_ORIGINS — дополнительные точные
HTTPS origins без пути/завершающего слеша. Не указывать `*`.

База не должна быть доступна из Интернета. Compose не публикует её порт; backend публикуется
только на 127.0.0.1. Хранить `.env` вне git, права 600 на Ubuntu; на Windows ограничить ACL.
Для отдельного сервера MySQL дополнительно настроить транспорт TLS/закрытую сеть: текущий
клиент не имеет env-настроек mysql TLS. Compose рассчитан на локальную закрытую сеть Docker.

Установить Nginx на хосте, скопировать crm-proxy.conf в `/etc/nginx/snippets/`, настроить
server_name и существующие cert/key пути в nginx.conf, проверить `nginx -t`, перезагрузить.
Получение/автообновление сертификата настроить отдельно. Лимит тела 1 MiB совпадает с API;
Excel <=512 KiB до Base64, распаковка <=8 MiB. Лимит входа Nginx дополняет лимит БД.
`/health/ready` проверяет схему; `/health/live` только процесс.

## Миграции

Файлы backend/migrations/001–008 применяются по имени, с advisory lock и SHA256 в
crm_migrations. Не менять уже применённые SQL: мигратор откажется продолжать при смене checksum.
Для локальной разработки `npm run migrate`; для сборки `npm run migrate:prod`.
Compose: `docker compose run --rm migrate`.

DDL MySQL делает implicit commit: миграции не являются одной транзакцией.
В старых миграциях ALTER TABLE не все restart-safe при падении посередине. При такой ошибке
остановить обновление, сохранить логи, сравнить схему с SQL и восстановить резервную копию
либо подготовить проверенную forward migration. Не удалять строки crm_migrations и не
запускать SQL вслепую повторно. Миграция 008 добавляет preview; старые 001–007 не изменены.
Readiness требует также 008. На первом запуске регистрация доступна после миграций.

## Backup и проверка восстановления

Скрипт `scripts/backup.mjs` использует Docker Compose и Node, одинаково на Windows/Ubuntu;
SQL передаётся байтами, без PowerShell-перенаправления с изменением кодировки.
Ограничение текущего скрипта: dump до 256 MiB в памяти; для больших БД нужен потоковый backup.

Остановить backend и всех внешних писателей для согласованности dump и row-count manifest:

```sh
docker compose stop backend
node scripts/backup.mjs backup backups/pre-update
docker compose --profile restore rm -sf mysql-restore
docker compose --profile restore up -d --wait mysql-restore
node scripts/backup.mjs verify-restore backups/pre-update
docker compose --profile restore rm -sf mysql-restore
docker compose start backend
```

Каждому backup новое имя каталога. `--single-transaction`, triggers/routines/events,
hex-blob; проверяются SHA256 файла, количество строк во всех таблицах, mysqlcheck.
Restore выполняется **только в отдельном tmpfs сервисе**, не в основной БД.
Не запускать интеграционные тесты на восстановленной рабочей копии: они модифицируют данные.
Для полной приёмки перед восстановлением в production проверить на изолированном backend
readiness, вход и чтение известных контрольных карточек/балансов. Автоматическая проверка
структуры и строк не заменяет такую бизнес-проверку.

Копировать backup и manifest в зашифрованное независимое хранилище, ограничить доступ,
назначить периодичность/retention и ответственного за регулярный restore drill.
Скрипт сам не создаёт cron/планировщик и не отправляет backup наружу.

## Обновление

1. Сохранить текущий код/образ и `.env`, остановить записи.
2. Сделать backup и пройти verify-restore. Не продолжать при ошибке.
3. Развернуть новую версию кода, прочитать новые миграции.
4. `docker compose build backend migrate`.
5. `docker compose run --rm migrate`.
6. `docker compose up -d --no-deps backend`.
7. Проверить `/health/ready`, вход, контрольную карточку и баланс; посмотреть логи.

Если миграция не прошла, не стартовать новую версию. Откат кода после изменения схемы
не гарантирует совместимость; восстановление согласованной копии базы и старого кода —
ручная процедура на остановленном сервисе. Для аварийного восстановления сначала
восстановить отдельную БД/volume, проверить её, затем переключить сервис и секреты.
Не выполнять `docker compose down -v` на production.

## Известные эксплуатационные особенности

- Все обращения организации сериализуются блокировкой строки организации: безопасно для беты,
  но ограничивает throughput, нагрузочные испытания не выполнены.
- Идемпотентность и подтверждённые preview сохраняются без TTL удаления ради безопасных повторов;
  нужна политика хранения/архивации. Истёкшие неподтверждённые preview тоже пока не удаляются.
- Нет мониторинга, внешнего лог-агрегатора и расписания backup по умолчанию.
- Публичная регистрация включена. Перед публичным запуском определить политику регистрации и защиты от злоупотреблений.
- Образы закреплены тегами patch-version; для supply-chain фиксации на сервере сохранить также digest.
