# Внутренний финансовый учёт

Все маршруты ниже имеют префикс `/api/v1`. Это регистрация операций в CRM, без эквайринга,
банковских переводов и платёжных провайдеров. Валюта — рубли, денежные значения — строки
целых копеек. Float для денег не используется. `amount` положительный, максимум 999999999999.

## Обновление

Из `backend`: `npm ci`, `npm run migrate`, `npm run build`, `npm start`.
Нужна настроенная `.env` и MySQL 8. Миграция `007_finance.sql` добавляет связи возвратов и
версии занятий, не переписывает старые проводки. `/health/ready` проверяет её наличие.
Сделайте резервную копию рабочей БД перед миграцией.

Новый обязательный параметр для возвратов — `originalPaymentId`. Старые клиенты нужно обновить.
Исторические возвраты, записанные до миграции без ссылки на оплату, не привязываются автоматически:
определить достоверную связь по сумме невозможно. Перед продолжением возвратов по старым оплатам
API блокирует новые возвраты и компенсацию оплат этого плательщика с
`LEGACY_REFUNDS_UNRESOLVED`, пока есть действующие несвязанные возвраты. Нужно сверить их и компенсировать/зарегистрировать их заново с верной ссылкой.
Предыдущие версии занятий до установки миграции нельзя восстановить из текущей карточки;
при первой новой операции сохраняется текущая версия, далее — все последующие.

## Раздельные счета

| Операция | Касса/банк (`cash`) | Лицевой счёт (`payer`) | Зарплатный счёт (`payroll`) |
|---|---:|---:|---:|
| Оплата | +сумма | +сумма | — |
| Возврат | −сумма | −сумма | — |
| Проведение, присутствие/прогул | — | −стоимость со скидкой | +ставка занятия |
| Уважительный пропуск | — | 0 | Ставка занятия сохраняется |
| Выплата зарплаты | −сумма | — | −сумма |
| Ручной расход | −сумма | — | — |
| Перевод | −источник, +получатель | — | — |

Положительный лицевой баланс — аванс, отрицательный — долг. Списание за обучение не является
повторным поступлением денег. Зарплата фиксирована за занятие, даже если все пропуски уважительные.
Выдача абонемента не создаёт оплату: это лимит занятий; стоимость обучения начисляется при проведении.
Касса не может стать отрицательной. Лицевой счёт может, в том числе после возврата.
Выплата ограничена начисленным остатком. Исправление уже оплаченного преподавателю занятия может
создать отрицательный зарплатный остаток — переплату, без фиктивного возврата денег в кассу.

## Операции API

Для всех финансовых POST (кроме создания счёта) нужны `X-CSRF-Token` и `Idempotency-Key`.

- `POST /accounts`: `{branchId,name}` — создать кассу/банковский счёт, директор.
  Оба типа денежного счёта хранятся как `cash`; различаются названием, например «Расчётный счёт».
- `POST /transactions`: `{kind,accountId,amount,reason,...}`. Возвращает `{operationId,entryIds}`.
  `payment` требует `payerId`; `refund` — `payerId` и `originalPaymentId`;
  `salary_payment` — `staffId`; `expense`/`income` не принимают получателя.
  Оплата/возврат доступны менеджеру и директору, расход/прочий доход/выплата — директору.
  `income` означает прочий доход, не аванс плательщика и не перенос остатка кассы.
- `POST /transfers`: `{fromAccountId,toAccountId,amount,reason}` — менеджер/директор,
  оба счёта должны быть денежными и доступными пользователю; счета различны.
- `POST /transactions/{operationId}/reverse`: `{reason}` — компенсировать всю ручную операцию.
  Для оплат/возвратов — менеджер/директор, остальных операций — директор.
  У проводки может быть только одна компенсация. Компенсации не сторнируются повторно.
  Оплату со связанными действующими возвратами сначала нужно освободить от них путём их компенсации.
  Проводки занятий этим маршрутом менять нельзя.
- `GET /accounts/{id}/balance`: текущий баланс.
- `GET /accounts/{id}/history?page=1&pageSize=50`: баланс, общее число и история проводок;
  `pageSize` ≤ 200. `operation_id` объединяет проводки операции, `reversal_of` связывает
  компенсацию с исходной записью, `original_entry_id` у возврата — проводка исходной оплаты
  на лицевом счёте. Плательщик видит только собственный счёт, менеджер — счета своих филиалов
  без зарплатных, директор — все счета организации.

### Частичный возврат

```json
{
  "kind": "refund",
  "accountId": "UUID_КАССЫ",
  "payerId": "UUID_ПЛАТЕЛЬЩИКА",
  "originalPaymentId": "OPERATION_ID_ИСХОДНОЙ_ОПЛАТЫ",
  "amount": "25000",
  "reason": "Частичный возврат по заявлению"
}
```

Исходная оплата должна существовать в той же организации, принадлежать тому же плательщику,
не быть компенсирована. Сумма действующих возвратов ≤ сумма оплаты. Компенсированный возврат
освобождает лимит. Проверка лимита, кассы и обе проводки атомарны. Возврат из другой доступной
кассы разрешён; доступ к плательщику и кассе проверяется отдельно.
`ORIGINAL_PAYMENT_REQUIRED` — нет ссылки, `INVALID_PAYMENT` — неподходящая оплата,
`REFUND_EXCEEDED` — превышение суммы, `PAYMENT_HAS_REFUNDS` — запрет компенсации исходной оплаты.

## Проведение и исправление

`POST /lessons/{id}/complete`:

```json
{
  "expectedRevision": 0,
  "reason": "Проведение занятия",
  "attendance": [{"studentId": "UUID_УЧЕНИКА", "status": "present"}]
}
```

Все участники текущего состава должны иметь одну отметку: `present`, `absent` или `excused`.
Неотмеченная посещаемость не считается прогулом. Будущее/отменённое занятие провести нельзя.
Педагог может впервые провести только собственное занятие, без изменения финансовых параметров.
Менеджер/директор могут исправлять проведённое занятие тем же endpoint с новой `expectedRevision`
и обязательной непустой причиной. В элементах attendance доступны `payerId`, `price`, `discount`
ИЛИ `discountPercent` (базисные пункты: 10000 = 100%), `subscriptionId` (null — убрать).
Новый плательщик должен быть связан с учеником и доступен в филиале.

На верхнем уровне доступны `teacherId` для замены преподавателя и `salary` для ставки.
Передать явную ставку может только директор. При замене преподавателя берётся его действующая
ставка, ранее заданная директором; проверяются филиал, активность и пересечения расписания.
Если преподаватель прежний, без `salary` сохраняется ставка занятия, а не текущая ставка сотрудника.
Для исправления времени или состава участников: отмена, создание правильного занятия и проведение.

Одна транзакция InnoDB выполняет проверку сессии, прав и версии, сохранение снимка, компенсацию
прежних списаний/зарплаты/использования абонементов, запись исправленных участников и посещаемости,
новые списания за present/absent, использование абонементов, начисление зарплаты, смену статуса,
снимок новой версии, аудит и сохранение ответа идемпотентности. Любая ошибка откатывает всё.
`POST /lessons/{id}/cancel`: `{expectedRevision,reason}` компенсирует проведённое занятие и
возвращает использования абонементов; доступен менеджеру/директору.
`GET /lessons/{id}/versions?page=1&pageSize=50` — сохранённые версии, включая состав, плательщиков,
скидки и посещаемость. Доступ менеджеру/директору; менеджеру ставка скрыта. Аудит содержит автора,
серверное время, причину и входные данные операции.

Округление: итог после процентной скидки округляется до копейки HALF_UP:
`payable = (price * (10000 - discountPercent) + 5000) / 10000` с целочисленным делением.
Пример: 101 коп., скидка 50% → 51 коп. к оплате, скидка 50 коп.
Фиксированная скидка больше цены отклоняется; отрицательного итога нет. Два типа скидки
в одном запросе запрещены; передача нового типа заменяет прежний.

## Идемпотентность и конкурентность

Уникальность `(org_id,key_value)` обеспечена MySQL. Все изменения организации сериализуются
блокировкой строки организации `SELECT ... FOR UPDATE`, включая проверку повторного ключа.
Тот же ключ и нормализованный запрос возвращают сохранённый результат после потери ответа.
Другой путь/тело/пользователь/права с тем же ключом → 409 `IDEMPOTENCY_CONFLICT`.
Ответ содержит новый requestId текущего HTTP-запроса, но прежний data, operationId и revision.
Неуспешная транзакция ключ не занимает. Безопасный retry использует тот же ключ; новая операция — новый.
Параллельные проведения с разными ключами и одной expectedRevision дают один успех и один
`STALE_REVISION`. Компенсации дополнительно защищены UNIQUE `(org_id,reversal_of)`.
Гранулярность блокировки сознательно консервативная для бета-версии: операции внутри организации
выполняются последовательно, это ограничение пропускной способности.

## Отчёт

`GET /reports/finance?from=<ISO>&to=<ISO>&branchId=<UUID>` — директор.
Период положительный, максимум 366 суток, `[from,to)` по времени записи проводки.
`branchId` необязателен. Зарплата и финансовый результат доступны только директору.
Компенсации учитываются со знаком в периоде своей записи, по типу исходной операции;
отчёт за прошлый период не переписывается задним числом.

- `payments`, `refunds`: деньги, фактически зарегистрированные в кассах, с компенсациями.
- `expenses`: ручные расходы; `otherIncome`: прочий доход.
- `tuitionAccrued`: начисленная стоимость обучения, включая компенсации.
- `salaryAccrued`, `salaryPaid`: начислено и отмечено выплаченным раздельно.
- `cashFlow = payments - refunds + otherIncome - expenses - salaryPaid + transfersNet`.
- **`financialResult = tuitionAccrued + otherIncome - expenses - salaryAccrued`**.
- `cashBalances`, `payerBalances`, `payerDebts`, `payroll[].balance` — остатки на момент `to`
  по всей истории до `to`, а не только за период; долг — модуль отрицательного лицевого баланса.
- `payroll[].accrued/paid` — начисления/выплаты каждому преподавателю за период.

Авансы, возвраты авансов, переводы и фактическая выплата уже начисленной зарплаты не меняют
финансовый результат. Остаток кассы не является прибылью. Модель — внутренний управленческий
результат, без налогов, амортизации, себестоимости запасов и дебиторских начислений прочих расходов.
При фильтре филиала кассовые операции относятся к филиалу кассы, обучение — к филиалу лицевого
счёта, зарплата — к филиалу зарплатного счёта. Межфилиальный перевод даёт ненулевой transfersNet
для отдельного филиала, ноль для организации целиком. Эти правила важны при оплате в другом филиале.

Старый `/analytics/overview.finance` — сводка движения денег, не отчёт о прибыли.
Полный машинный контракт: `docs/openapi.json`.
