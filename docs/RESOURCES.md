# API ресурсов CRM

Все URL ниже начинаются с `/api/v1`. Данные реальны: ответы читаются из MySQL,
сервер не добавляет демонстрационные записи. Организация создаётся транзакционно
через `/auth/register`, текущая организация доступна через `/organization`.

## Запуск обновления

Из `backend`: `npm ci`, настройка `.env`, `npm run migrate`, `npm run build`, `npm start`.
Новая миграция — `005_resources.sql`; миграции 001–004 не изменены.
Перед обновлением рабочей базы сделайте резервную копию. Миграция добавляет
версии, архивные отметки, периоды членства, связи плательщиков и историю;
существующие ученики сохраняют основного плательщика. Их связи переносятся в
`crm_payer_students`. Старое членство получает время начала на момент миграции:
историческая дата не выдумывается; её можно уточнить через API.

## Ресурсы и карточки

| URL | Назначение |
|---|---|
| `/organization` | Настройки текущей организации; создание через регистрацию |
| `/branches` | Филиалы |
| `/rooms` | Аудитории и вместимость |
| `/people` | Общая личность, имя, дата рождения, контакты |
| `/payers` | Роль плательщика, заметка `comment` |
| `/students` | Роль ученика, активность, основной `payerId` |
| `/payer-students` | Дополнительные связи плательщиков с учениками, `relationship` |
| `/staff` | Сотрудники и преподаватели: предмет, ставка, статус |
| `/companies` | Юридические лица; уникальность ИНН внутри организации |
| `/tasks` | Задачи, дата срока, приоритет, ответственный и связанные объекты |
| `/groups` | Группы, преподаватель, вместимость, статус и даты |
| `/enrollments` | Периоды зачисления учеников в группы |
| `/leads` | Лиды и явная конвертация |
| `/lead-stages`, `/pipeline` | Порядок этапов и реальные количества лидов по этапам |

Коллекции: `GET /resource`, `POST /resource`.
Карточки: `GET /resource/:id`, `PATCH /resource/:id`,
`POST /resource/:id/archive` с `{}`.
Для организации используется `/organization` без `:id`.
Архивирование не удаляет запись и не освобождает уникальные контакты/ИНН.
Архивные карточки доступны по ID и с фильтром; их изменение запрещено.
Архивирование организации делает tenant доступным только для чтения.

Для каждой карточки есть `GET .../history`, `GET .../comments`, `POST .../comments`
с `{ "text": "..." }`. В комментариях сервер устанавливает `author_id` и
`created_at`; клиент не может их подменить. Списки комментариев и истории
пагинированы, содержат имя автора. История хранит состояние до и после изменения,
автора, время и действие. История начинает накапливаться после обновления;
события до установки миграции не реконструируются. Внутренние комментарии и
история доступны только сотрудникам в рамках прав на карточку; ставки скрыты
от недиректоров. Уведомления и старый `/comments` сохранены.

Преподаватели используют `/staff`; роль `teacher` для аккаунта по-прежнему
назначается директором через существующий механизм пользователей.

## Версия и конкурентное редактирование

У карточек есть числовое поле `version`, начальное значение 1.
`PATCH`, архивирование, конвертация лида и выход из группы требуют заголовок
`If-Match: "1"` (значение версии в двойных кавычках).
Отсутствие заголовка — `400 VERSION_REQUIRED`; старая версия —
`409 VERSION_CONFLICT`. Не повторяйте конфликтующий запрос с новой версией
автоматически: сначала покажите пользователю актуальную карточку и его правки.
Изменение и запись истории выполняются в одной транзакции.

```ts
await fetch(`/api/v1/people/${person.id}`, {
  method: 'PATCH', credentials: 'include',
  headers: {
    'Content-Type': 'application/json',
    'X-CSRF-Token': csrfToken,
    'If-Match': JSON.stringify(String(person.version)),
  },
  body: JSON.stringify({ name: 'Новое имя' }),
});
```

`PATCH /people/:id` сохраняет отсутствующие поля; `contacts: []` явно очищает
контакты. Остальные формы обновления принимают набор полей, указанный в OpenAPI
(не следует считать их произвольным JSON merge patch).
`PATCH /profile` также требует версию из `GET /profile` → `person.version`.
Изменение имени синхронизирует имена в связанных карточках сотрудников/лидов
и повышает их версии. Добавление комментария не меняет версию карточки.

## Списки

Общий ответ: `{ items, page, pageSize, total }` внутри `{ data, requestId }`.
`page` начинается с 1; `pageSize` — 1–100, по умолчанию 25. Некорректные и
неизвестные параметры отклоняются. Поиск `q` — буквальная подстрока, символы
LIKE экранируются. Плательщики/ученики ищутся по имени общего человека,
зачисления и связи — по имени ученика.

| Параметр | Поддержка |
|---|---|
| `sortBy=id`, `sortOrder=asc/desc` | Все коллекции |
| `sortBy=name` | Именованные карточки, плательщики, ученики, зачисления, связи |
| `sortBy=version` | Новые ресурсы с версиями |
| `sortBy=status` | Ресурсы с бизнес-статусом |
| `sortBy=capacity` | Группы, аудитории |
| `sortBy=date/priority` | Задачи |
| `sortBy=starts_at/ends_at` | Зачисления, занятия |
| `branchId` | Ресурсы филиалов; для branches фильтрует ID самого филиала |
| `status` | Бизнес-статус; для people/students/branches — active/inactive |
| `status` для enrollments | active/ended/future/archived |
| `status` для остальных без бизнес-статуса | active/archived |
| `archived=exclude/only/all` | Новые ресурсы; по умолчанию exclude |
| `personId` | payers, students, staff, leads, tasks |
| `payerId` | students, payer-students, tasks, leads |
| `studentId` | enrollments, payer-students, tasks, leads |
| `groupId` | enrollments, lessons |
| `responsibleId` | tasks, leads |
| `teacherId` | groups, lessons |
| `priority` | tasks |

Неподдерживаемое данным ресурсом поле сортировки/фильтра возвращает `400`.
В сортировке используется ID как дополнительный стабильный ключ.
`/pipeline?branchId=...` использует те же права, исключает архивные лиды.

## Люди, контакты и роли

Email обрезается по краям и приводится к нижнему регистру до проверки.
Телефон приводится к E.164: `8 (999) 123-45-67` → `+79991234567`.
Уникальность `(org_id, kind, value)` обеспечивается и БД. Повтор нормализованного
контакта в одном запросе — ошибка валидации; контакт другого человека —
`409 CONTACT_EXISTS`. Объединения людей по контакту нет, в том числе при импорте.

Создайте человека один раз и передавайте его `personId` в `/payers`, `/students`,
`/staff` и `/leads`. У каждой роли есть уникальность `(org_id, person_id)`.
Один человек может быть одновременно сотрудником, плательщиком и учеником.
`/students` требует `payerId`; именно этот основной плательщик используется
существующим учётом занятий. Дополнительные `/payer-students` не меняют
основного плательщика автоматически. Основную связь нельзя архивировать,
пока не выбран другой основной плательщик. Связи могут охватывать филиалы
одной организации при наличии у сотрудника доступа к обеим сторонам.
Межорганизационные ссылки запрещены также составными внешними ключами.

## Группы и зачисления

`POST /groups/:id/members`: `{ studentId, startsAt?, endsAt? }`.
Без `startsAt` используется серверное текущее время; `endsAt` по умолчанию null.
Ответ содержит ID членства, его `version` и `groupVersion`.
`POST /enrollments`: `{ groupId, studentId, startsAt, endsAt }`.
`PATCH /enrollments/:id`: `{ startsAt, endsAt }` с версией членства.
Временные метки — ISO 8601 со смещением, в БД UTC.

Период полуоткрытый `[startsAt, endsAt)`. Ученик может быть в нескольких группах,
но пересекающиеся членства в одной группе отклоняются. Студент, человек,
филиал и группа должны быть активны, группа и ученик — в одном филиале.
Период должен помещаться в даты группы, если они заданы.
Алгоритм проверяет максимальное количество пересекающихся периодов,
включая будущие: соседние непересекающиеся периоды используют одно место.
Уменьшение вместимости проверяет и членства, и запланированные списки занятий.

`DELETE /groups/:id/members/:studentId` с версией группы завершает текущие
периоды серверным временем и отменяет будущие, сохраняя строки и историю.
Повторное зачисление создаёт новый период. Архивирование группы завершает
членства; списки прошлых занятий и финансовые проводки сохраняются.
`GET /groups/:id/members` возвращает периоды, включая завершённые/отменённые,
с учётом прав на учеников. Общая коллекция `/enrollments` поддерживает фильтры.

Существующая блокировка строки организации `FOR UPDATE` сериализует проверки
и записи. Она защищает конкурентное зачисление и изменение вместимости,
включая несколько экземпляров API с одной БД. Это консервативная стратегия
беты: запросы одной организации сериализуются, высокая нагрузка отдельно
не проверялась. Доступ приложения к БД должен оставаться единственным путём
бизнес-записей; ручной SQL не выполняет проверки вместимости API.

## Лиды

Порядок из `frontend/src/crm/config/modules.ts`:
`Не разобран` → `Назначен контакт` → `Назначена проба` → `Проведена проба` →
`Получена оплата`; отдельный этап — `Отказ`. API допускает явный переход
между любыми этими этапами и записывает состояние до/после в историю.

Создание принимает ровно один из `person` (новый человек) или `personId`
(явно выбранный существующий человек). Конвертация:
`POST /leads/:id/convert` с `If-Match` и `Idempotency-Key`.
Тело: `{ mode?: "payer" | "payer-student", payerPersonId?, studentPersonId? }`.
По умолчанию `payer-student`, оба человека — человек лида. При выборе
существующих людей проверяются организация, доступ и филиал лида.
Результат `{ leadId, payerId, studentId, version }`; в режиме payer studentId=null.
Повтор с тем же ключом возвращает сохранённый результат. С другим ключом и
актуальной версией возвращает те же связи; другой набор целей — `409`.
Смена этапа на «Получена оплата» не конвертирует лид и не создаёт оплату.

## Задачи и доступ

Поля: `branchId`, `name`, `date` (срок-дата), `priority`
(`Обычный`, `Высокий`, `Низкий`), `status` (`Новая`, `В работе`, `Выполнена`),
`responsibleId`, `personId`, `studentId`, `payerId`, `comment`.
Ссылки проверяются в текущей организации и филиале задачи; архивные цели
и неработающий ответственный не принимаются. Если у ответственного есть
аккаунт, проверяется его доступ к связанным объектам.
Директор/менеджер создают и редактируют задачи; преподаватель меняет статус
только доступной ему назначенной задачи через `PATCH /tasks/:id/status`.
Текущая видимость ученика/человека также проверяется при чтении задач преподавателем.
